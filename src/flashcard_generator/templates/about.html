Recall: Comparing Single-Prompt and Multi-Stage LLM Flashcard Generation

Research build — project description

Abstract. Recall turns study notes into flashcards with a large language model (LLM). This build exists to study one question: is a multi-stage pipeline (fact inventory, omission audit, drafting, review, repair) worth its extra cost compared with asking a model once? The intended comparison covers token consumption, estimated cost, time, and accuracy. The pipeline and per-stage token counting are implemented. The single-prompt baseline, cost and time measurement, accuracy evaluation, and the results pages are not yet implemented (see section 9).

1. Research question

Asking an LLM for flashcards in one prompt is cheap and fast, but a single answer can skip facts, invent details, or write unclear questions. Splitting the work into several checked stages may fix some of this, but every stage adds requests, tokens, and waiting time. The open questions are:

  1. RQ1. Does the multi-stage pipeline produce more accurate and more complete cards than a single prompt?
  2. RQ2. What does that cost in tokens, money, and time?
  3. RQ3. How do the control variables (section 4) and the choice of model change the answers to RQ1 and RQ2?

No results are claimed here. This page describes the setup, not findings.

StatusNot implementedImplemented
Table 2. Pipeline stages.
StageRuns once perJob
inventorysectionList every testable fact in the section, each with an exact quote from the notes.
audit_inventorysectionRe-read the section and correct the list: add missed facts, remove unsupported ones.
draftbatch of factsWrite question/answer cards covering the facts in the batch.
reviewbatch of factsCheck each card against its facts and return the corrected batch.
repairbatch with gapsOne extra review-style request for facts that still have no accepted card.

Between stages, ordinary Python code (not the model) rejects quotes that do not appear in the source, tautological or empty cards, duplicates, and conflicting answers to the same question.

The coverage report on the Run page is not an accuracy score. It counts facts the model itself found that ended up on a card, so it cannot show what the model missed or misunderstood.

6. How a run works

  1. The browser sends the notes, model, and options to the server.
  2. The server starts a background job and immediately returns a job ID.
  3. The page asks for the job's status about every 1.2 seconds and shows progress text.
  4. The job splits the notes into sections and runs the stages in Table 2, counting tokens after each request.
  5. When it finishes, the server saves the run to its local database (timing, tokens, cards, facts) and the page displays the result.

7. Terminology

LLM
Large language model: a program that writes text in reply to text it is given. Here, Gemini.
Prompt
The text sent to the model, including instructions and the data to work on.
Token
The unit a model reads and writes; roughly a short word or part of a word. APIs count and price in tokens.
Input / output tokens
Tokens sent to the model versus tokens it writes back. Output usually costs more per token.
Thinking tokens
Tokens some models spend reasoning before answering; typically billed like output.
Single-prompt baseline
Generating all the flashcards in one request. The reference point for the comparison.
Multi-stage pipeline
A fixed sequence of requests in which each one does a narrow job (Table 2).
Section (chunk)
A piece of the notes up to CHUNK_SIZE characters, cut at paragraph or sentence boundaries where possible.
Fact inventory
The list of testable statements found in a section, each with an exact source quote.
Audit
A second pass over a section that corrects the fact inventory.
Batch
Up to BATCH_SIZE facts handled together in the draft and review stages.
Repair
An extra request for facts that no accepted card covers.
Grounding
Requiring a claim to point to text that really appears in the source. Here: the quote must be found in the section.
Coverage
The share of identified facts that are represented by an accepted card. It is not accuracy.
Hallucination
Model output that sounds plausible but is not supported by the source.
Structured output
Asking the model to reply in a fixed JSON shape so that code can read it reliably.
Temperature
A setting for how random the model's wording is. Lower values give steadier output.
Rate limit (RPM, RPD, TPM)
Caps on requests per minute, requests per day, and tokens per minute. The free tier's request caps are low enough to matter for a multi-stage pipeline.
Control variable
A setting kept the same during a comparison so that only the thing being studied changes.
Recall / precision
Of the facts that should be on cards, the share that are (recall); of the cards produced, the share that are correct (precision).

8. Limitations

  • The model that extracts facts also reviews the cards, so errors can be correlated; a reviewer can share the writer's blind spots.
  • Quote matching proves that a quote exists in the notes, not that the card interprets it correctly.
  • The free tier's request limits can interrupt long runs, and failed or retried requests also count against them.
  • Scanned PDFs, diagrams, and handwriting are not supported (no OCR).
  • Automated tests use scripted model replies, so they check the pipeline's logic, not real-model quality.
  • Single-user, local app; finished jobs are kept in memory for at most 30 minutes.
